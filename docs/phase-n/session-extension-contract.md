# Extension contract
A session permits one short-lived proposal and at most one applied ten-minute extension. Proposal lifetime is centrally configured, initially 60 seconds and capped by the original deadline. Requesting records that participant's consent; the other participant must approve the exact proposal ID. Either can decline/withdraw while pending. An expired/declined/unavailable proposal is terminal, preventing repeated nagging or automatic continuation.

Only current authenticated participants can act. The session must be ACTIVE, N-controlled, not already extended, currently eligible/unblocked and independently listener-qualified, with both I participant pulses fresh. A new-listener readiness lease is not required during an already active chat: I intentionally turns acceptance readiness off when leaving the workspace. Current active-session presence is the applicable availability evidence.

The transaction takes I's advisory lock and ordered participant capacity locks. A unique session proposal, immutable original deadline and consent timestamps, a guarded APPLIED transition and a database timer trigger permit exactly one +600-second change. Both approvals refer to that same row. Next commitments for either participant, including cross-role bookings, and queue-origin staffed coverage must fit the extended end plus the captured break. Pending proposals do not secretly reserve extra time; a later booking can make approval unavailable.

Repeated applied approvals return the same result. End, revocation, interruption, expiry and a changed commitment cannot be overridden. Original appointment instants stay immutable; the live request displays its actual extended deadline. Approved retention cleanup is the only separate terminal-only path that clears expired duration metadata, never a live clock.
