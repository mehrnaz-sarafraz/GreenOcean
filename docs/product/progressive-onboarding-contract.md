# Progressive onboarding contract

Three optional stages: topics, support style, privacy/service boundaries. No health history, diagnosis, role selection or clinical consent is required. Zero selections, skip each stage, skip all, back, reload and edit later are valid. Defaults are already private before onboarding. Finishing never toggles privacy or content controls.

Owner preferences persist NOT_STARTED, IN_PROGRESS, SKIPPED or COMPLETED plus last confirmed step (0–3). LEGACY_UNKNOWN is an explicit compatibility state for old onboardingComplete=true records; it is not evidence of completion. New false records become NOT_STARTED. The old boolean remains a navigation-dismissed compatibility field: true for SKIPPED/COMPLETED/LEGACY_UNKNOWN, false for new/in-progress. Explicit entry starts IN_PROGRESS; each Continue persists before advancing. Only step 3 can complete. Skip persists SKIPPED without saving unfinished topic/style input. Individual stage skip preserves prior confirmed values. Failed saves do not advance or replace saved preferences.

Progress is server-side and owner-scoped; no unfinished sensitive input or per-click analytics is stored. Concurrent partial updates lock the owner row to avoid unrelated-field loss. Explicit [] clears topics and empty string clears support style; null/omitted fields preserve values for older clients. Old onboardingComplete writes can dismiss as LEGACY_UNKNOWN but cannot fabricate COMPLETED.

Stable topic slugs replace display labels only with an unambiguous catalog mapping. Unmapped historical labels are retained owner-only in a legacy field for review/clear/export, never inferred or recommended. Sensitive topic collection is **disabled by default**, including API injection, pending a documented legal/product basis and applicable special-category decision. Empty/clear remains enabled. Existing choices are retained privately without new processing; no diagnostic inference. An environment gate may only be enabled after that external review. Topics are not used to promise personalized feed ranking; Phase I must review any future usage. No third-party or user-level onboarding analytics is enabled; status is operational owner data, not anonymous measurement.

Support style optionally chooses a real first destination: SHARED_EXPERIENCES → feed; SUPPORT_GROUPS → communities; LISTENER → Support discovery; PROFESSIONAL_KNOWLEDGE → articles; empty/skip → Support. Navigation is an allowlist, never a supplied URL; existing account/geographic authorization remains required and unavailable services fall back to Support discovery with a truthful explanation. No conversation, group join, appointment or elevated role is created. Member onboarding never navigates to a professional application; the existing dedicated profile entry remains available.

Peer/community and listener support are non-clinical. Educational articles are not treatment. Professional care depends on credentials, jurisdiction, capacity and an appropriate relationship. Availability is never guaranteed. Guest urgent-help access remains available. Return/edit entry is offered from Profile and Privacy & Safety. English/Persian and RTL use the existing language context and design tokens.
