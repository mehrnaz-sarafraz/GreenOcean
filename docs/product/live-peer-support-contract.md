# Live peer support contract — Model A

Entry navigation never creates a request. A member explicitly creates an idempotent short-lived offer to a currently qualified, ready, authenticated listener. The direct pathway has no offline fallback, implicit queue or auto-retry and no clinical topic requirement. Support is text-only, non-clinical and not an emergency or continuously monitored service. Existing feed/community/articles and public urgent-resource routes remain independent choices.

Presence, discoverability, readiness, acceptance and active conversation are distinct. Readiness belongs to one current authenticated session and rotating lease; default heartbeat 15s and freshness 45s. Another device can explicitly take readiness, invalidating prior lease renewal. Background/unmount stops readiness; auth revocation invalidates its evidence. No stored online flag qualifies a listener. Current approved application, all active coursework and independently recorded staff practice/code approval are necessary. Legacy approvals/roles are retained but never inferred as independent live approval. Staff routes retain administrative enablement, role checks and recent MFA. Global live enablement defaults false pending genuine staffing, supervision, regional and Phase J approvals.

REQUESTED expires at server creation +90s. Only the targeted listener can accept; only the member can explicitly activate within 60s of acceptance. Acceptance reserves capacity but does not create a conversation. Activation atomically creates exactly one LISTENER service conversation linked to the request; ordinary personal DIRECT conversations are not reused. The member and listener each have at most one open role capacity; cross-role overlap is also rejected under a database advisory transaction lock. A partial unique index independently prevents duplicate open rows per member and per listener. Business transitions use database clock after serialization, never transaction-start or device time.

ACTIVE participant foreground pulses are distinct from listener availability. Missing either pulse beyond 45s makes the session INTERRUPTED; sending is stopped. Both current eligible participants must renew to resume within 120s measured from the actual stale deadline, not from first delayed cleanup. Otherwise the session completes with CONNECTION_TIMEOUT, capacity releases and it cannot reopen. Either party may end immediately. These bounded technical defaults are configurable and captured in each request; they do not infer crisis or authorize intervention. Any production change to expectations/retention remains an owner launch decision.

Server reads/actions lazily reconcile deadlines; a bounded scheduled sweep also reconciles idle rows. A delayed scheduler/restart cannot make a stale acceptance/send valid or permanently reserve capacity. Bidirectional block, account/qualification/regional revocation invalidates live activity. Database triggers and the same transaction advisory lock serialize safety changes with acceptance/activation/message insertion. No process-local lock is relied on. No request ever returns from a terminal state.

Messaging reuses existing conversations/messages, sender identity, limits and reporting. A client idempotency UUID prevents duplicate live message inserts; a changed body with the same key is a conflict. No messaging before activation or after completion/interruption/safety termination. History of completed authorized sessions remains readable subject to membership/account/block rules; safety-ended and unlinked historical listener conversations fail closed, are preserved, and are not silently activated. A report uses existing conversation membership and never automatically copies a transcript or grants unrestricted staff access.

Presence is transient and deleted when stale. No topic, diagnosis, onboarding preference, journal or message text enters new analytics. No analytics pipeline is introduced. Request metadata retention and safety-evidence preservation are open Phase J launch requirements, not an indefinite-retention promise. Existing message retention/erasure is preserved. Owner exports include participation metadata and only own authored listener messages so another participant's revoked content is not re-exposed through export. Account erasure removes new presence/request/authorization data using the existing lifecycle. Previously received copies cannot be recalled; no E2EE or absolute confidentiality is claimed.

Phase N adds separately gated explicit [future bookings](listener-scheduling-contract.md) and [bounded waiting](listener-waiting-queue-contract.md). Both hand off to this same request/accept/activate lifecycle. Queue expiry cannot destroy an already atomically transferred valid I request. Calendar availability and staffing windows never replace actual I readiness. Existing historical requests receive no retroactive duration; new N-controlled requests capture a thirty-minute deadline at activation, enforced by reconciliation and the existing messaging guard.
