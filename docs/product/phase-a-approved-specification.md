# GreenOcean — Phase A: Full Implementation, Migration, Security & Testing

تو نقش یک تیم ارشد توسعه محصول، Backend، Frontend، امنیت کاربردی، معماری داده و مهندسی کیفیت را بر عهده داری.

پروژه:

- Repository: `mehrnaz-sarafraz/GreenOcean`
- Backend: Java 21, Spring Boot, Spring Security, PostgreSQL, Flyway, Maven
- Frontend: React Native, Expo, TypeScript, Expo Router
- Platforms: Web, Android, iOS

## مأموریت اصلی

تمام نیازمندی‌های مصوب فاز A، از A-01 تا A-06، را در پروژه موجود GreenOcean پیاده‌سازی، اصلاح، یکپارچه و آزمایش کن.

**باید ابتدا کد واقعی را به‌طور کامل بررسی کنی. هر چیزی که درست و کامل پیاده‌سازی شده، حفظ شود؛ هر چیزی که ناقص است اصلاح شود؛ و فقط قابلیت‌های واقعاً موجودنبوده اضافه شوند.**

این پروژه نباید بی‌دلیل بازنویسی شود.

هدف، دستیابی به یک محصول قابل‌اعتماد، با امنیت و حریم خصوصی قابل‌آزمون و قابل‌توسعه است؛ نه صرفاً اضافه‌شدن فایل، Endpoint یا صفحه.

پس از بررسی اولیه، اجرای تغییرات را ادامه بده. صرف ارائه برنامه یا پیشنهاد برای این مأموریت کافی نیست.

# بخش ۳ — A-01: سیاست سن و مجوز دسترسی

## سیاست مصوب محصول

نسخه فعلی GreenOcean دارای عرضه مرحله‌ای است:

- کاربران بزرگسال واجد شرایط، ۱۸ سال به بالا: دسترسی به قابلیت‌های اجتماعی تعاملی پس از فعال‌سازی حساب.
- افراد ۱۳ تا ۱۷ سال: فعلاً فقط منابع عمومیِ انتخاب‌شده و مناسب سن، بدون حساب اجتماعی.
- افراد زیر ۱۳ سال: دسترسی به منابع عمومی مناسب و کمک فوری، بدون ایجاد حساب اجتماعی.

بخش تعاملی نوجوانان در این مأموریت ساخته نمی‌شود.

## نیازمندی‌ها

- شرایط سن در Backend کنترل شود.
- روش احراز شرایط سن از نتیجه آن جدا باشد.
- خوداظهاری به‌عنوان احراز مستقل ثبت نشود.
- سن یا تاریخ تولد کامل بدون ضرورت ذخیره نشود.
- امکان افزودن ارائه‌دهنده مستقل Age Assurance در آینده فراهم باشد.
- حساب فاقد شرایط مجوز انتشار، پیام خصوصی، گفتگو با شنونده یا ورود به گروه‌های اجتماعی نداشته باشد.
- منابع عمومی بدون حساب در دسترس باشند.
- محتوای خصوصی یا پست‌های کاربران بزرگسال به‌صورت خودکار وارد منابع عمومی نشوند.

## قرارداد دسترسی

مجوز عملیات باید بر اساس وضعیت حساب، شرایط سن، نقش، محدودیت‌های امنیتی و دسترسی منطقه‌ای تعیین شود.

اگر برای اولین پایلوت از خوداظهاری بزرگسالی استفاده می‌شود، ضعف این روش ثبت شود و وضعیت آن به‌صورت `SELF_ATTESTED` از تأیید مستقل متمایز باشد. ادعای جلوگیری قطعی از دروغ‌گفتن درباره سن مجاز نیست.

## Frontend

- اطلاع‌رسانی واضح درباره شرایط سن.
- مسیر جایگزین برای فرد فاقد شرایط.
- نمایش منابع عمومی بدون اجبار به ثبت‌نام.
- عدم نمایش محتوای نامناسب یا خصوصی در مسیر عمومی.

## Backend

- اعتبارسنجی مستقل از Frontend.
- کنترل مجوز در Endpointهای تعاملی.
- جلوگیری از ارتقای غیرمجاز وضعیت احراز سن.
- خطاهای ساختاریافته و قابل‌فهم.

## Database

- نگهداری حداقل شواهد لازم از بررسی شرایط سنی.
- تمایز روش خوداظهاری و بررسی مستقل.
- طراحی قابل‌مهاجرت برای حساب‌های موجود.

# بخش ۴ — A-02: کشور، استان، شهر و منطقه خدمات

## سیاست مصوب

از کدهای مرجع بین‌المللی استفاده کن:

- Country: ISO 3166-1 alpha-2
- Subdivision: ISO 3166-2، در صورت پوشش مناسب
- City: شناسه پایدار مکان از داده مرجع معتبر، مانند GeoNames

از Enum عظیم برای تمام شهرها استفاده نکن.

## الزامات

- طراحی کاتالوگ نسخه‌دار کشورها.
- ارتباط صحیح کشور، استان و شهر.
- امکان جست‌وجو و نمایش نام محلی.
- جلوگیری از کد کشور یا شهر نامعتبر.
- جداکردن کشور محل اقامت، کشور فعلی و زبان ترجیحی.
- اختیاری‌بودن شهر در ثبت‌نام.
- دریافت شهر فقط هنگام نیاز به قابلیت محلی.
- جداکردن داده مکان از مجوز ارائه خدمات در آن مکان.

سرویس‌ها باید بتوانند به‌صورت مستقل در هر کشور فعال یا غیرفعال شوند:

`COMMUNITY`, `LISTENER`, `PROFESSIONAL_DIRECTORY`, `PROFESSIONAL_CARE`, `URGENT_RESOURCES`

وضعیت:

`AVAILABLE`, `UNAVAILABLE`, `LIMITED`, `UNDER_REVIEW`

## محدودیت مهم

فعلاً پنل مدیریت کشورها لازم نیست.

از داده مرجع و پیکربندی سمت سرور استفاده کن.

تا زمانی که کشورهای مجاز پایلوت مشخص نشده‌اند، هیچ کشور جدیدی را بدون پیکربندی صریح برای ارائه خدمات محدودشده فعال نکن.

برای Development و Test، مقادیر آزمایشی مستقل و مشخص تعریف کن؛ آن‌ها نباید ناخواسته به Production منتقل شوند.

## Frontend

انتخاب‌گر جست‌وجوپذیر کشور و، در زمان نیاز، انتخاب وابسته استان و شهر.

## Backend

اعتبارسنجی شناسه‌های مکانی و دسترسی منطقه‌ای خدمات.

## Database

کاتالوگ مکان‌ها و تنظیمات دسترسی خدمات با Migration غیرمخرب.

# بخش ۵ — A-03: حساب پایه و نقش‌های حرفه‌ای

## سیاست مصوب

تمام کاربران عادی ابتدا نقش پایه `USER` دریافت می‌کنند.

انتخاب MEMBER/PROFESSIONAL از ثبت‌نام اولیه حذف شود.

## درخواست نقش حرفه‌ای

متخصص‌شدن از گردش‌کار مستقل انجام شود:

1. ثبت درخواست
2. دریافت اطلاعات حرفه‌ای موردنیاز
3. بارگذاری امن مدارک
4. بررسی انسانی
5. تأیید یا رد
6. اعطای مجوز تخصصی پس از تأیید

برای Listener نیز از گردش‌کار آموزشی و تأییدی موجود استفاده کن.

## امنیت نقش‌ها

- کاربر نتواند برای خودش نقش حرفه‌ای تأییدشده صادر کند.
- نقش Admin از فرم عمومی یا APIهای کاربری قابل درخواست نباشد.
- اعطای Moderator و Admin فقط از مسیر داخلی مجاز انجام شود.
- تغییر نام نمایشی یا عنوان پروفایل نباید وضعیت تأیید حرفه‌ای ایجاد کند.
- مجوز دسترسی نباید صرفاً به ادعای Frontend یا Payload وابسته باشد.
- وضعیت حساب، نقش، وضعیت تأیید و مجوز عملیات مستقل باشند.
- دسترسی حساس مدیریتی نیازمند کنترل قوی‌تر، از جمله MFA مناسب پیش از بهره‌برداری واقعی باشد.

سیستم درخواست حرفه‌ای فعلی را بررسی و تا حد ممکن استفاده مجدد کن.

# بخش ۶ — A-04: وضعیت حساب و حذف اطلاعات

## مدل هدف

وضعیت اصلی حساب:

`PENDING`, `ACTIVE`, `SUSPENDED`, `DELETED`

فرایند حذف مستقل:

`REQUESTED`, `PROCESSING`, `COMPLETED`, `FAILED_RETRYABLE`, `ON_HOLD`

اگر ساختار فعلی با مدل جدید تفاوت دارد، ابتدا سازگاری داده و Migration را طراحی کن.

## قواعد اصلی

- حساب جدید پیش از تأیید ایمیل، وضعیت `PENDING` دارد.
- حساب `PENDING` مجوز عملیات اجتماعی حساس ندارد.
- وضعیت `ACTIVE` پس از تحقق شرایط لازم اعطا می‌شود.
- حساب `SUSPENDED` نمی‌تواند محدودیت را با Refresh Token دور بزند.
- عملیات حذف حساب تمام نشست‌های مربوط را باطل می‌کند.
- `DELETED` به معنای نگهداری نامحدود اطلاعات شخصی نیست.

## Email Verification

قبل از اجباری‌کردن تأیید ایمیل، مسیر ارسال واقعی ایمیل، انقضا، یک‌بارمصرف‌بودن توکن، کنترل تلاش ناموفق و ارسال مجدد را تکمیل کن.

از زیرساخت `email_outbox` موجود استفاده مجدد کن؛ توکن یا کد خام نباید در لاگ‌ها باقی بماند و Payloadهای حساس باید حفاظت و پاک‌سازی مناسب داشته باشند.

برای کدهای کوتاه، در برابر حدس آفلاین و تلاش پرتکرار محافظت لازم برقرار شود.

## مهاجرت حساب‌های قبلی

- حساب‌های قدیمی را به‌صورت خودکار تأییدشده اعلام نکن.
- آن‌ها را ناگهانی و بدون مسیر فعال‌سازی مسدود نکن.
- فرایند اطلاع‌رسانی، تأیید تدریجی و Feature Flag مناسب داشته باش.
- رفتار مهاجرت را با داده تست مشابه حساب‌های قدیمی آزمایش کن.

## حذف داده

چهار مفهوم باید جدا باشند:

- Delete Account
- Delete Post
- Delete Message For Me
- Delete Message For Everyone

ابتدا قابلیت‌های موجود را بررسی کن.

حذف حساب را در محدوده این فاز تکمیل کن. اگر حذف پیام برای خود و همه وجود ندارد، نیازمندی مستقل و وابستگی‌های آن را مشخص کن؛ تغییرات بزرگ پیام‌رسانی را بدون طرح و تست مربوط، به‌صورت مخفیانه وارد این فاز نکن.

## حفاظت داده

- ابطال دسترسی
- خروج اطلاعات از نمایش عمومی
- پاک‌سازی یا ناشناس‌سازی طبق سیاست
- قواعد مشخص برای داده‌های گزارش‌شده
- سیاست نگهداری نسخه‌های پشتیبان
- حفظ حداقل داده فقط در صورت وجود دلیل معتبر
- آزمون کنترل مالکیت و جلوگیری از حذف داده دیگران

هیچ وعده‌ای درباره حذف فوری از تمام نسخه‌های پشتیبان بدون زیرساخت واقعی داده نشود.

# بخش ۷ — A-05: ثبت‌نام حداقلی و حریم خصوصی

## هدف

ثبت‌نام اولیه فقط اطلاعات ضروری را دریافت کند.

اطلاعات پیشنهادی:

- Email
- Password
- اطلاعات حداقلی لازم برای شرایط سن
- پذیرش نسخه معتبر Terms
- Country of Residence فقط اگر برای سیاست عرضه ضروری باشد

## اطلاعاتی که باید از ثبت‌نام اولیه حذف یا اختیاری شوند

- City
- Display Name
- Username
- Avatar
- انتخاب Professional
- Support Topics
- Diagnosis
- Treatment History
- اطلاعات پزشکی غیرضروری

اگر معماری موجود برای ایجاد Profile به Username یا Display Name نیاز دارد، شناسه و نام موقت امن و غیرقابل‌استنتاج از ایمیل تولید کن.

کاربر قبل از اولین مشارکت عمومی بتواند اطلاعات نمایشی خود را بررسی و تغییر دهد.

## حریم خصوصی پیش‌فرض

- پروفایل خصوصی
- مکان مخفی
- سال تولد مخفی
- محتوای حساس محوشده
- کنترل‌های قوی‌تر نمایش محتوا روشن
- درخواست پیام از ناشناس‌ها خاموش
- امکان شروع گفتگوی درخواستی با شنونده یا متخصص از مسیر مجاز
- عدم افشای ترجیحات حمایتی در پروفایل عمومی

## قوانین و پذیرش

- نسخه Terms باید در Backend اعتبارسنجی شود.
- پذیرش در سرور با زمان و نسخه سند ثبت شود.
- Privacy Notice از رضایت اختیاری جدا باشد.
- هیچ رضایت اختیاری پیش‌فرض فعال نباشد.
- نسخه جدید اسناد و نیاز احتمالی به پذیرش مجدد طراحی شود.
- داده‌های رضایت و پذیرش از اطلاعات حساس سلامت جدا نگهداری شوند.

## امنیت رمز عبور

با توجه به NIST SP 800-63B-4:

- برای حساب‌های مبتنی بر رمز به‌عنوان تنها عامل، حداقل ۱۵ کاراکتر.
- پشتیبانی از رمز طولانی حداقل تا ۶۴ کاراکتر.
- عدم الزام قراردادی به ترکیب عدد، حرف بزرگ یا نماد.
- اجازه استفاده از Password Manager و Paste.
- بررسی رمزهای ضعیف یا افشاشده.
- ارزیابی محدودیت طول ورودی BCrypt موجود.
- حفظ سازگاری با رمزهای Hashشده قبلی و طراحی ارتقای تدریجی.

## Frontend

- ثبت‌نام ساده
- خطاهای فیلدمحور
- نمایش و مخفی‌کردن رمز
- مدیریت خطا و قطع اینترنت
- جلوگیری از ارسال تکراری
- فرم سازگار با موبایل و دسترس‌پذیری مناسب

## Backend

- اعتبارسنجی مستقل
- ثبت پذیرش قوانین
- حفاظت در برابر درخواست پرتکرار
- وضعیت اولیه مناسب حساب
- جلوگیری از افشای وجود حساب در فرایندهای حساس
- جلوگیری از اعتماد به داده‌های کلاینت برای تصمیم امنیتی

از تکرار آزاردهنده هشدار در تمام صفحات خودداری کن.

## Backend

کنترل نقش، وضعیت تأیید و مجوز عملیات.

## Moderation

کنترل جعل تخصص، سوءاستفاده از عنوان حرفه‌ای و گزارش توصیه پزشکی خطرناک.

اگر تشخیص خودکار محتوای خطرناک واقعاً وجود ندارد، آن را موجود فرض نکن؛ قابلیت گزارش و رسیدگی انسانی را صادقانه توصیف کن.

# بخش ۹ — امنیت تکمیلی و الزامات مشترک

این بخش برای تکمیل امن A-01 تا A-06 ضروری است.

موارد موجود را ابتدا بررسی کن:

- JWT
- Refresh Token Rotation

- Rate Limiting
- Token Storage
- Audit Logging

## الزامات

1. استاندارد امنیتی هدف: OWASP ASVS 5.0.
2. سیاست رمز: NIST SP 800-63B-4.
3. پیش‌فرض حریم خصوصی: Data Protection by Design and Default.
4. اعتبارسنجی ورودی در Backend.
5. جلوگیری از Enumeration در ورود و بازیابی.
6. محدودسازی حدس رمز و کد تأیید.

9. جلوگیری از دسترسی بین حساب‌ها.
10. حفاظت از عملیات حساس با احراز هویت مجدد در صورت نیاز.
11. عدم نگهداری Refresh Token حساس در Web localStorage.
12. بررسی معماری امن Web Session، مانند BFF یا Cookie امن HttpOnly با حفاظت CSRF.
13. حفظ ذخیره‌سازی امن Mobile.
14. مدیریت Secrets از طریق محیط امن و عدم Commit آن‌ها.

تغییر مکانیزم نشست وب و موبایل باید جداگانه تست و به‌صورت سازگار مهاجرت داده شود.

# بخش ۱۰ — چهار شخصیت اجباری تست

برای **تمام قابلیت‌های کاربرمحور و تمام کنترل‌های حساس A-01 تا A-06** حداقل چهار دسته تست طراحی کن.

این چهار دسته باید سناریوهای واقعی و قابل‌اجرا داشته باشند، نه صرفاً نام‌گذاری Test Class.

## Persona 1: Happy Path

کاربر واجد شرایطی که عملیات را درست انجام می‌دهد.

نمونه‌ها:

- ثبت‌نام بزرگسال واجد شرایط.
- تأیید ایمیل معتبر.
- ورود و خروج موفق.
- تکمیل یا رد ترجیحات اختیاری.
- مشاهده اطلاعات مناسب منطقه.
- ایجاد درخواست متخصص بدون دریافت نقش پیش از تأیید.
- درخواست حذف حساب توسط مالک.

## Persona 2: Creative User

کاربری که مسیرهای غیرمعمول اما مجاز را امتحان می‌کند.

نمونه‌ها:

- استفاده از رمز طولانی و Unicode.
- تغییر زبان در وسط ثبت‌نام.
- رهاکردن فرم و بازگشت.
- انتخاب نکردن هیچ موضوع حمایتی.
- تغییر کشور و درخواست اطلاعات شهر.
- استفاده از مرورگر و موبایل برای یک حساب.
- ارسال درخواست‌های هم‌زمان مجاز.
- تغییر پروفایل و ترجیحات پس از فعال‌سازی.
- استفاده از امکانات حداقلی بدون تکمیل پروفایل.

## Persona 3: Confused User

کاربری که اشتباه می‌کند یا فرایند را متوجه نمی‌شود.

نمونه‌ها:

- فرمت اشتباه ایمیل.
- رمز نامعتبر.
- واردکردن کد منقضی.
- اشتباه گرفتن کشور با شهر.
- تلاش برای ورود قبل از تأیید ایمیل.
- ارسال چندباره فرم.
- قطع اینترنت وسط فرایند.
- تلاش برای ورود به بخش متخصص بدون صلاحیت.
- انتخاب ناقص یا اشتباه ترجیحات.
- درخواست کمک در نبود شنونده فعال.

سیستم باید پیام روشن، رفتار قابل‌بازیابی و عدم از دست رفتن غیرضروری اطلاعات ارائه دهد.

## Persona 4: Malicious User

تست فقط در محیط ایزوله با داده‌های ساختگی اجرا شود.

نمونه‌ها:

- دورزدن شرط سن از طریق API.
- دست‌کاری Country Code یا شناسه شهر.
- تلاش برای دریافت نقش Admin یا Professional از طریق Payload.
- دسترسی به داده حساب دیگر.
- استفاده از Token منقضی یا باطل‌شده.
- استفاده مجدد از Refresh Token قدیمی.
- حدس پرتکرار کد تأیید.
- ارسال درخواست‌های غیرعادی به Endpointهای عمومی.
- تلاش برای حذف حساب فرد دیگر.
- تغییر فیلدهای وضعیت حساب.
- تلاش برای مشاهده منابع یا گفتگوهای خصوصی بدون مجوز.
- دست‌کاری شناسه نسخه قوانین.
- تلاش برای فعال‌کردن مجوز با تغییر فقط Frontend.
- ورود پس از تعلیق یا حذف حساب.

نتیجه همه تست‌ها باید مشخص و قابل‌گزارش باشد.

## سناریوهای End-to-End اجباری

E2E-01: Welcome → Register → Verify Email → Activate → Login

E2E-02: کاربر زیر سن مجاز → جلوگیری از حساب تعاملی → منابع عمومی

E2E-03: ثبت‌نام → رد ترجیحات اختیاری → استفاده از بخش مجاز

E2E-04: ورود → تغییر پروفایل → خروج → ورود مجدد

E2E-05: ثبت‌نام بدون پذیرش معتبر قوانین → رد امن درخواست

E2E-06: تلاش برای استفاده اجتماعی با حساب PENDING → رد در Backend

E2E-07: درخواست نقش متخصص → وضعیت Pending Review → عدم دسترسی حرفه‌ای

E2E-08: تعلیق حساب → ابطال دسترسی و Refresh Token

E2E-09: بازیابی رمز → تغییر رمز → ابطال نشست قبلی

E2E-10: حذف حساب → ابطال نشست → عدم نمایش پروفایل

E2E-11: تغییر کاربر روی یک دستگاه → عدم مشاهده داده کاربر قبلی

E2E-12: انتخاب کشور بدون ظرفیت خدمات → نمایش پیام و مسیر جایگزین

E2E-13: مراجعه بدون حساب به محتوای عمومی → عدم دسترسی به داده‌های خصوصی

E2E-14: ارسال هم‌زمان درخواست Refresh → نتیجه کنترل‌شده

E2E-15: خطای شبکه وسط ثبت‌نام یا Onboarding → بازیابی امن و تجربه قابل‌فهم

- Professional Applicant

- پیش‌فرض‌های حریم خصوصی بررسی شوند.

- Pull Request و گزارش تغییرات آماده بازبینی باشند.

اگر هرکدام از این معیارها محقق نشده، وضعیت فاز را Complete اعلام نکن.

# بخش ۱۷ — قالب گزارش نهایی

فهرست فایل‌های تغییرکرده، دلیل تغییر و نیازمندی مرتبط.

## C. Database Migrations

نام Migrationها، اثر داده‌ای و نتیجه تست سازگاری.

## D. API Contracts

Endpointهای جدید یا اصلاح‌شده و تغییر رفتار آن‌ها.

مشکلات امنیتی کشف‌شده، اصلاحات و ریسک‌های باقی‌مانده.

## G. Persona Testing

- Complete & Tested
- Implemented, Awaiting Runtime Verification
- Partially Complete
- Blocked
- Not Started

# دستور نهایی

ابتدا کد را با دقت بررسی کن، سپس بر اساس قرارداد محصول A-01 تا A-06، تمام تغییرات لازم را به‌صورت غیرمخرب و سازگار اجرا کن.

روی کد موجود توسعه بده؛ نه اینکه بی‌دلیل آن را از ابتدا بازنویسی کنی.

بعد از هر تغییر مهم تست بگیر و خطاها را اصلاح کن.

تمام قابلیت‌های جدید باید به چهار گروه تست Happy Path، Creative User، Confused User و Malicious User مجهز باشند.

تا حد امکان کار را در همین مأموریت کامل کن و صرفاً به تحلیل یا تولید TODO بسنده نکن. اگر محدودیت واقعی محیطی، قانونی یا دسترسی مانع بخشی از کار شد، بخش‌های قابل‌اجرا را تکمیل و مانع را دقیق گزارش کن.

هدف این است که Phase A به یک پیاده‌سازی یکپارچه، قابل‌تکرار، قابل‌آزمایش، قابل‌بررسی در Pull Request و آماده ارزیابی برای پایلوت تبدیل شود.

هیچ ادعای امنیت کامل، انطباق قانونی قطعی یا آمادگی انتشار بدون شواهد معتبر نداشته باش.
