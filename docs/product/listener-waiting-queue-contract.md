# Listener waiting queue contract
The queue is a distinct, explicit, non-emergency opt-in pathway. Navigation and status reads never admit a member. Admission requires current account/region eligibility, enabled Phase I and queue/duration gates, genuine qualified authenticated listener readiness, an independently approved current staffing window, no conflicting participant commitment, and room within the central queue cap (initially 100, validated range 1–500). A profile or future calendar alone is never coverage.

A currently busy listener counts as coverage only with a valid actual readiness lease, an active captured bounded session expected to free capacity inside the twenty-minute window, no conflicting calendar commitments and sufficient approved staffing. Interrupted, unbounded legacy, offline or merely future-scheduled listeners do not count. Staffing approval requires current independent MODERATOR/ADMIN authority and recent security-key authentication. Windows are explicit, bounded to 24 hours, with at most 14 upcoming windows per listener; they never automatically turn readiness on. No production staffing windows are seeded.

One active entry per member. PostgreSQL fixes admission and expiry exactly twenty minutes apart; refresh, devices, worker delay and reload never renew them. FIFO applies among currently eligible entries. Approximate earlier-entry counts reveal no other identities and are not an ETA. Explicit language is optional; health topics and inferred distress are never used.

A ready listener receives one temporary allocation, up to the central initial 60 seconds and never beyond the parent deadline. The member must confirm the exact allocation ID while current. Only then is one independent Phase I REQUESTED row created, atomically linked as TRANSFERRED. Real listener acceptance and explicit member activation remain mandatory. No earlier step creates chat.

An unanswered proposal is terminal and releases capacity. Expired/cancelled entries do not requeue. Cancellation of a transferred pending Phase I request uses existing I controls; an active conversation uses end controls. Parent expiry never destroys an already-transferred valid I request. Disabling only the queue cancels WAITING/OFFERED entries, while valid transferred I requests retain their independent lifecycle. Disabling underlying I still terminates live support.

Notices are generic, optional, deduplicated and preference-aware. No real external push delivery is claimed. All production gates remain disabled until actual staffing and processing/retention approvals are satisfied.

An already-admitted WAITING entry can span a temporary readiness gap while a qualified, independently staffed listener window still exists. Its original twenty-minute deadline remains and the UI explicitly says no listener is ready. This does not admit new members without actual coverage or reserve a listener. Removing actual staffing/qualification or changing the member commitment terminates the wait. An already-OFFERED proposal is withdrawn if readiness disappears; it is never silently reassigned. This preserves Phase I's required readiness reset between real conversations.
