## Confirmed K fixes

K first live run reproduced four same-owner/target report requests returning201,201,201,409 instead of one201 and three409. ReportService checked then inserted without shared transaction serialization. ReportRepository now takes a per-reporter/type/target PostgreSQL advisory transaction lock before the duplicate check. No historical report is deleted or migration rewritten. A four-thread genuine-PG regression plus the unchanged real HTTP assertion verify one open record across concurrent callers.

The initial npm scan matched critical [GHSA-pqg4-j6r4-53mv](https://github.com/advisories/GHSA-pqg4-j6r4-53mv) in shell-quote1.10.0, transitive through react-devtools-core. The lock now resolves compatible1.11.0 using official npm metadata/integrity, with no Expo major change. A regression verifies rejection of all four line terminators after a comment token and never invokes a shell. It is a build-tool dependency issue, not evidence that account API text reached a production shell.

## Advisory triage — scans are not a clean bill of health

The first completed scan matched31 Maven package/advisory pairs across113 resolved runtime coordinates, and13 npm vulnerable-package records including one critical. These are advisory matches, not31 reproduced application exploits. Complete final inventory/severity/qualification is in dependency-findings.json and the final scan artifact. The scanner job succeeds when it produces complete evidence; findings remain triage inputs and deployment gates. It does not silently suppress advisories or automatically authorize release.

Source review finds no Tomcat container DIGEST/FORM/JNDI authentication, no configured HTTP/2/AJP connector, no Spring SSE view-fragment/XSLT rendering, no Jackson default typing/identity references/InetAddress/Path/XMLGregorianCalendar application DTOs, and no custom Log4j MapMessage JSON use. These observations narrow attack paths but do not certify every transitive path unreachable. [Tomcat's own advisory list](https://tomcat.apache.org/security-11.html) and [Spring's SSE advisory](https://spring.io/security/cve-2026-47890/) specify conditions; database labels can differ from vendor severity. Current Spring security remains JWT/bearer based, not container FORM/DIGEST authentication.

Remaining Jackson/httpcomponents/Log4j/PostgreSQL/Tomcat/Spring and npm build/router advisories require targeted security-owner qualification or compatible patching before pilot/production. Default JDBC TLS/channel-binding requirements, build-tool untrusted inputs and router malformed URI handling need deployment-specific review. Do not use npm audit's suggested Expo downgrade/major replacement blindly. No broad framework upgrade is performed merely to clear a dashboard. Pilot/production remain blocked until the security ledger is resolved, alongside legal/human/native prerequisites.
