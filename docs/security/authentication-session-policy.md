# GreenOcean authentication and session policy — E/F

Approved product contract, implementation baseline d135328;2026-10-26. This document describes enforceable controls and rollout limits, not certification. Members use password authentication with an AAL1-aligned target; no full ASVS L2 or AAL2 service claim. Email ownership, adult self-attestation, local screen privacy and server MFA are distinct.

## Verified references and normative discipline

NIST SP800-63B-4 (2025 final), sections3.1.1.2,3.2.2,4.1.2,4.2,4.6,5.1 and5.2 were read directly at https://pages.nist.gov/800-63-4/sp800-63b.html . Its SHALL clauses include sufficient single-factor password length, protected verification, throttling and authenticated channels. AAL2 entails independent factors and an offered phishing-resistant method. Recommendations (SHOULD), permissions (MAY) and GreenOcean values below have different force; local timeout choices are risk decisions, not universal NIST mandates.

OWASP ASVS5.0.0 (published30May2025), official tagged requirements: https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.csv . IDs are version-qualified; the control matrix maps targeted evidence, not the entire standard. Full L1 assessment remains outstanding, including production compromised-password corpus, TLS/deployment and frontend hosting controls.

OWASP MASVS2.1.0, release https://github.com/OWASP/masvs/releases/tag/v2.1.0 and official https://mas.owasp.org/MASVS/ : MASVS-STORAGE-1/-2, AUTH-1/-2/-3, NETWORK-1/-2 and PLATFORM-1/-3 guide storage, lifecycle and link boundaries. Device validation remains a separate requirement.

OWASP Authentication, Session Management, Forgot Password, Multifactor Authentication and Credential Stuffing Prevention Cheat Sheets were read directly from https://cheatsheetseries.owasp.org/cheatsheets/ (corresponding *_Cheat_Sheet.html pages). They are living implementation guidance, checked2026-10-26, not versioned normative standards. Exact source links and verified IDs appear in control-coverage.md. Expo SDK57 versioned docs, including SecureStore, govern native APIs. Yubico java-webauthn-server2.10.1 is used for WebAuthn validation; it provides ceremony validation, not application authorization or an AAL certification.

Session duration env overrides use GREENOCEAN_SESSION_WEB_OVERALL/WEB_IDLE/MOBILE_OVERALL/MOBILE_IDLE/PRIVILEGED_OVERALL/PRIVILEGED_IDLE/RECENT_AUTH. Duration values must be positive, idle <= overall. Access JWT remains existing GREENOCEAN auth configuration. Keep configured session bounds within approved policy; changing these values is an operational policy change, not an automatic NIST update.

## Compatibility, proxy and rollout

V37 adds fields to existing sessions and credential/challenge storage. Historical client type is unknown; labels are untrusted and cannot safely distinguish browsers from phones. Existing sessions receive LEGACY scope and the stricter24hour overall/30minute idle limits from original created/last-used times (never migration time); PENDING1hour/15minute and privileged12hour caps apply. Credentials/roles/social content are preserved; there is no blanket revoke or reset. Already over-bound sessions will require login after deployment, including older mobile sessions. Communicate this stricter compatibility behavior before authorizing production migration. New client sessions get endpoint-selected WEB/MOBILE limits. Initial deployment must coordinate backend and client changes; forward recovery is preferred over rolling back to code that ignores timeout fields.

Trust req.remoteAddr only. Default server.forward-headers-strategy=NONE; an ingress may use an explicitly reviewed trusted proxy configuration that strips incoming forwarding headers and supplies validated origin/client data. Never enable generic forwarded-header trust on an Internet-facing direct backend. Production exact HTTPS origin list and secure cookies remain required. SameSite does not replace Origin/custom-header CSRF checks. TLS termination, HSTS/CSP/referrer/no-store on static hosting and CDN logs must be configured and tested by the operator; do not put tokens in URL query strings or log fragments.

Security event retention applies only SECURITY-category records; it does not purge legal/moderation evidence. Default200 stored events per actor/hour bounds DB cardinality; shared anonymous bucket is intentionally coarse. Operational log sampling/rate controls and external alerts must be configured; usernames and health behavior must not be added to fraud logs. Security email acceptance is not inbox delivery.

## Approved deferred and blocked scope

E12 consumer passkey rollout and E13 optional member MFA are deferred. Reuse the credential repository/ceremony architecture later with explicit assurance policy; do not display inactive member setup buttons. ADMIN/MODERATOR staff endpoints are the privileged surface; routine professional/listener service access remains gated by existing roles/verification/region rather than a blanket MFA requirement. Administrative review of professional/listener credentials goes through staff endpoints and requires the same strong gate.

Production admin-enabled remains false and existing startup guard refuses it. Enabling an MFA development flag alone must never remove that guard. Real RP ID, HTTPS origin, approved staff accounts, independently issued first-enrollment permits, hardware/recovery policy and operator audit process are deployment dependencies. Lost/stolen factors: another enrolled approved key can step up for replacement; otherwise revoke account sessions/factors through a separately authorized, dual-reviewed operator procedure, verify staff identity out of band and issue a new short-lived enrollment permit. No public password/email reset endpoint grants staff assurance. Emergency recovery requires independent audit and incident review; there is no shared bypass secret.
