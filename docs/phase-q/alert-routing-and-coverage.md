# Actual alert transport and acknowledgement

All outbound alert activity defaults off. Operations, alert dispatch and technical signal detection have separate explicit configuration. Destinations are trusted deployment configuration (`GREENOCEAN_ALERT_PRIMARY_URL`, `GREENOCEAN_ALERT_ESCALATION_URL`), not URLs supplied by API callers. Production transport requires HTTPS without user-info, query or fragment and an independent signing key of at least32 UTF-8 bytes. No default signing key or destination is provided. Only the test profile permits explicitly loopback HTTP. No redirect or response-body retention is allowed.

An actual current staffing operator proposes a domain/recipient/destination-key route, with expiry at most30 days. A second independent staffing operator approves the proposal; the actual designated recipient separately acknowledges the assignment using current purpose/MFA. Current account/roles and expiry/revocation are checked for dispatch. Role removal atomically revokes old routes and cancels queued/claimed deliveries; role regrant cannot revive them. The staff screen reports transport configured separately from proven delivery. Real contact identity, contracts, on-call responsibility, operating hours and acknowledgement drills are not supplied by repository fixtures.

Active incidents enqueue one alert per current route. The payload contains only opaque incident/delivery references and fixed domain/kind/severity/state; it excludes evidence references, subject/recipient identities, narratives, keys and tokens. `X-GreenOcean-Delivery` and a HMAC-SHA256 signature over the exact JSON bytes accompany each request. Receiver implementations must authenticate the signature and deduplicate the stable delivery ID. Sending is at-least-once: a crash after remote acceptance and before local persistence can resend the same ID.

Workers claim with SKIP LOCKED and a30-second lease, commit before network I/O, bound each request to four seconds and connection setup to two seconds, and retry at most five times with bounded exponential delay. A shared PostgreSQL budget limits dispatch attempts to60/minute across instances; each sweep handles at most ten. FAILED remains visible. Revoked/expired routes stop further authorization; an already transmitted request cannot be recalled.

States: QUEUED → CLAIMED → DELIVERED or bounded retry/FAILED; actual current recipient acknowledgement changes DELIVERED → ACKNOWLEDGED. A provider2xx response means transport acceptance only. It is not proof of human receipt, staffing availability, a response-time commitment or successful incident resolution. Escalation uses a separate current independently approved level-one route after the configured30–3600-second interval when no actual human acknowledgement exists. Acknowledgement before escalation suppresses new escalation. Production remains nonoperational without real destination verification and real participant drills.

Actual local HTTP tests cover valid signatures, no private payload fields, delivery versus human acknowledgement, route revocation/current role checks, deduplication, five-attempt failure, recovery of expired claims, escalation and competing workers. These are synthetic receiver/account tests, not real on-call drills or proof of external provider authorization.

Dispatch runs in a separate single-worker executor with an atomic in-flight guard and no waiting work queue; repeated scheduler ticks cannot accumulate duplicate network jobs. Actual slow-receiver regression verifies the scheduler caller returns while the receiver is blocked and only one request is dispatched. Shutdown interrupts/bounds worker termination and closes the HTTP client. Source admission/retention schedulers do not wait for this outbound network request.
