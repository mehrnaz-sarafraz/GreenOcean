# Q4 controlled workload plan

Base: validated Q3 commit `035879e196e99ed1ffc1097c3363acf7287040b0`,PR30,Actions41786139282. Q4 is synthetic local validation,not production approval.

`PhaseQ4LoadRunner` is an explicitly invoked test-class main,excluded from the production jar. It refuses any database except `jdbc:postgresql://127.0.0.1:55432/greenocean_q4_load_qa` and requires `GREENOCEAN_LOAD_QA=isolated-only`. Run compiled test classes with the Maven-resolved test classpath. Reuse/create100 eligible synthetic client accounts,ensure their public post/private journal/mood fixtures exist,and provision a separate100-account login cohort so normal login session caps do not invalidate measured participants. Three additional synthetic purpose/professional reviewers prepare current notices and one text episode. The only payment provider bean is the explicit test configuration;no production adapter is fabricated.

At each concurrency25,50,75,100,perform two measured windows,each preceded by5 seconds warmup. Default measured window20 seconds;explicitly configurable10–120. Each simulated user has at most one HTTP request in flight and250ms think time. Duration includes the last in-flight responses. Client and server share CPU/JVM;the final run uses768MiB heap,PostgreSQL128MiB shared buffers/max100 connections and QA application pool3.

Profiles include all15 requested categories:registration/login,feed,anonymous publication,comments,group membership/read,own journal,mood,catalogue/courses,listener schedules/own queue,professional directory,new appointments,synthetic payment state callbacks,authorized clinical signaling,and purpose-scoped staff cases. The base nine read profiles are each weighted twice;four private/social write profiles once. Registration/login/membership are added per actor;10 participants have new booking/payment steps,one current participant has clinical signaling andone staff actor has case handling. There are no100 concurrent clinical video calls. Fresh free/paid slots are prepared per window;warmup substitutes reads for registration/login/booking/capture so new booking/capture transitions occur during measurement. Fixture metadata is explicitly synthetic,not proof of qualified humans,real notices,actual staff coverage or real provider acceptance.

Successful-read preflight must pass. The test keeps real throttles and duplicate guards:429 is separately reported;only the two exact existing publishing-protection409 messages are classified as protective. Any other non-success response fails the exercise after saving evidence. Responses are consumed in the synthetic client but never exported;artifacts contain fixed workload names,status groups,timings and aggregate resource metrics,not tokens,URIs,IDs or private bodies. Successful-only latency is separate from total latency/throughput. Login/registration all originate at one loopback IP;their protective rejections cannot be called successful authentication throughput.

p50/p95 require20 samples in the reported group;p99 requires10000. Do not pool windows with differing throttled mixes to invent p99. One-second samples capture CPU time/load,heap,GC count/time,Hikari active/idle/waiting,PostgreSQL commit/rollback/deadlock counters/lock waiters,queue depth and alert backlog. Sampling may miss shorter peaks;the delivery worker is not exercised by this load mix and has separate bounded signed-HTTP regression tests.

The initial diagnostic series recorded missing fixture prerequisites and duplicate-publication protection honestly;it was not used as a capacity pass. Final measured evidence and per-profile counts are in load-test-results/evidence JSON. Remaining staging qualification includes independent client IPs,longer duration,approved representative course/resource data,actual provider/network latency,worker saturation,current human coverage and separately authorized infrastructure. Those are open launch gates,not invented passes.
