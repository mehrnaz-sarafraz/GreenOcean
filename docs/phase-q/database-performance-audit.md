# Q4 PostgreSQL performance audit

The minimized16-plan artifact records execution time,relation/index names,row counts and buffer counters without SQL literals,private filters or row bodies. Feed queries are reconstructed from the current repository constants; other probes are representative paths, not a claim that every ORM-generated statement was measured. Authorization,journal,membership,listener booking/queue,appointments,capture/refund lookup,clinical grants,moderation,retention,reward and erasure state are covered. Empty/sparse tables do not establish representative service throughput. Full archive/erasure workflows and SQL function internals need staging profiling.

The first diagnostic configuration had PostgreSQL shared buffers only400KiB. A direct legacy feed offset2000 took1966ms on the smaller synthetic dataset. The controlled128MiB-buffer repeat on the later larger dataset measured: first feed page about41.9ms; direct deep offset850.0ms; cursor after position1000,27.3ms; own journal0.7ms; queue state0.03ms. These are individual EXPLAIN ANALYZE observations, not latency percentiles. See the JSON artifact for exact values and plans.

The actual defect fixed here is the public legacy feed's previously unlimited OFFSET. `PostService.feed` now rejects offsets beyond100 positions and invalid sizes/pages before database work; first-page behavior remains compatible. Existing cursor-based discovery remains available and the current social UI already uses it. Regression tests verify the budget and preserve the followers-only visibility boundary. The direct deep-offset diagnostic remains in the audit script for comparison, although that input is no longer reachable through the public feed API. Permission predicates were preserved.

Existing indexes support current-purpose membership,own journal,listener booking/queue,appointment,refund,clinical grant and reward lookup. The native feed uses ordering/permission functions and changes plans at deep offsets; the measured fix bounds that workload rather than adding speculative indexes. No index was added to an existing business table. V88 adds only the subject/purpose lookup needed by its new restoration restriction table. Its write/migration scope is additive; populated87→88 rollback/retry and unchanged source data are tested.

QA load used Hikari3/max PostgreSQL connections100;100-way booking contention used Hikari10. Sampled pool waiting peaked83 in the mixed series, so pool contention is a demonstrated limit. Increasing the pool alone is not a capacity guarantee: authorization SQL,CPU and database write contention must be remeasured together. Bounded alert delivery already runs on a separate single-task executor; no microservice extraction or distributed transaction was introduced.

Runtime PostgreSQL statement_timeout and lock_timeout remain0 in this local cluster; deadlock_timeout1s. These are an **open deployment resource-budget item**, not an endorsed production setting. Proposed staging evaluation: bound runtime statement/pool/lock waits separately from Flyway migrations and long account-rights work; verify timeout cancellation,rollback,truthful responses and retries against the approved budgets. A timed-out actual PostgreSQL query rolls back and its connection handles the next request. Two-connection recovery-review/authority-revocation races and100-way booking assert invariants; the mixed series observed no deadlock increment. No unapproved blanket migration timeout was applied.

Pagination remains an audit boundary outside the fixed legacy feed: own archive volume,large retention batches,deep legacy searches and populated clinical/financial plans need larger staging data. Preserve the existing cursor and bounded-batch paths. Database restart is a real process exercise; payment/refund,reward,clinical grant and source-approval contention suites remain separate from performance measurements.
