# Q4 conditional pilot capacity recommendation

The local technical observation is25–100 concurrently simulated clients for the documented short mixed HTTP workload. At100 clients,successful p95 wasabout149ms and175ms in the two final windows,with0 unexpected responses;protective rejections are separately counted. The worst successful p95 in the full series was230.356ms at75 clients. Exactly80 synthetic payment captures and80 free bookings committed without duplicate capture/slot booking. This does not mean100 simultaneous video calls or real clinical readiness.

The measured machine has6 physical/12 logical cores and7.42GiB RAM. The shared client/server JVM was capped768MiB; sampled heap peaked180122912 bytes. PostgreSQL had128MiB shared buffers and the application pool3. Pool waiting peaked83. CPU measurements include the simulated client,JSON handling and sampler,so they cannot be quoted as a standalone application-server CPU requirement. Local disk/network were not independently characterized. The accumulated527 account records include pending synthetic registration attempts;the desired **real pilot remains an explicitly authorized100–500-participant cohort**.

Recommendation: **do not authorize a100-concurrent-user production launch from this evidence**. Begin a separately approved staging rehearsal at25 concurrent clients,then repeat50/75/100 with realistic independent client IPs,durations,content distribution,provider/network latency and current human coverage. Raise an operational cap only after those source-specific measurements and approvals. No real cohort was recruited and no cap/feature was operationally enabled here.

Scaling options to evaluate: tune pool size against measured SQL/CPU/locks together;retain bounded independent workers;use existing cursor pagination;set separately reviewed runtime/migration timeout budgets;measure account-rights/retention batches;test real durable object/key recovery. A larger pool can move the bottleneck to PostgreSQL and must not be treated as a universal fix. The current modular Spring transaction model is retained;no measured benefit justifies extracting microservices.

Planning assumptions,not vendor quotes: separate client load generation from the application/database;reserve resources for measured heap plus native memory,OS cache and database working set;budget encrypted database/object backups and independent keys;limit media according to an actually approved provider and available supervised professionals. No defensible audio/video bandwidth,real-provider throughput,storage growth rate or infrastructure price was measured,so none is invented. Clinical media,payments and record operation remain independently NO_GO until their specific dependencies are approved.

Operational tradeoffs: lower concurrency and supported hours reduce staffing/latency risk;additional replicas require shared source gates,idempotent workers and actual recovery rehearsal;stronger RPO proposals cost durable/replicated storage and provider reconciliation. All proposals await a real owner and infrastructure operator. See per-service Q5 assessments rather than promoting a single all-platform launch conclusion.
